1M 上下文之外，人类还能做什么？

凡能装进1M上下文之内的任务，AI已经能够执行得比人更好，我们不得不开始思考AI取代人类的可能性。

1. 背景

自从 2022.11.30 OpenAI发布ChatGPT3.5以来[1]，生成式大模型的能力已经得到了显著的提升，从最开始的简单问答，发展到现在能够使用工具、编写软件、参与科研，开始接手工作流里越来越多的任务：

  • 在编程领域，benchmark从最开始的简单函数补全[2]，转变到需要先理解仓库、定位问题再修改代码的SWE-bench[3]，且最新模型的解决率都已经达到80%以上。
  • 在科研领域，Google DeepMind已经探索了基于Multi-Agent系统的AI科研方式[4]；而OpenAI近期 (2026.09.08) 更是宣布通过1万个左右的并发Agent在88小时内解决了 Navier–Stokes 千禧年问题[5]。

编程是有明确目标、已知答案的任务，而科研是高度开放式的任务，当前AI已经能够很好地完成这两个领域内的任务，说明无论是知识复用、还是知识生产，AI都有超越人类智能的趋势。

2. 现状

2.1. 注意力机制

现有的大模型无一例外地是基于Attention机制构造的，最原始的Self-Attention公式如下：

Attention(Q,K,V)=softmax⁡(QKTdk)VAttention(Q,K,V)=\operatorname{softmax}(\frac{QK^T}{\sqrt{d_k}})V Attention(Q,K,V)=softmax(dk​​QKT​)V

简单理解，这个公式计算了token两两之间的相关性，QQQ矩阵代表了每个token想要取回什么样的信息，KKK矩阵代表了每个token有哪些信息，QKTQK^TQKT通过点积表达token两两之间信息上的相关性，最后通过对VVV矩阵进行加权得到汇总结果。

原始注意力机制最大的问题在于其计算复杂度是O(n2)O(n^2)O(n2)的，也就是随着输入长度线性增长，计算量按平方来增长，主要原因就在于计算QKTQK^TQKT得到的是一个n×nn \times nn×n的矩阵。当模型的上下文窗口从8K增长到1M时，计算量增长了1252=15625125^2=156251252=15625。

过去几年，研究者们尝试对原始Attention做了很多改造来降低计算量，比如Sparse Attention将全局注意力改成局部注意力；Linear Attention通过核化来将Attention的计算复杂度降低到O(n)O(n)O(n)。但是原始Full Attention表达能力实在太好，这些新Attention机制都不能完全替代。

因此大模型上下文的增长目前仍受O(n2)O(n^2)O(n2)复杂度掣肘。

2.2. 新知识获取

大模型在预训练阶段学习到语料库内包含的世界知识，也就是说，当预训练完成之后，内化在大模型参数里面的知识只是过去世界的快照。当询问大模型知识库截止日期之后的新知识时，回答的正确率会非常低[6]。

目前一般有两种解决方式：

  • RAG (retrieval-augmented generation)：在运行时根据用户的输入去数据库内查询相关知识，然后注入到大模型的上下文中作为知识补充 (给大模型配备Web Search工具是一样的)。这种方式的有效性高度依赖于知识库数据质量和召回的准确性，否则召回的垃圾信息只会浪费上下文，甚至导致模型性能劣化。
  • Fine-tuning：通过LoRA等方式对模型参数进行微调，从而把新的世界知识内化到新模型参数里。但是这种方式也可能导致灾难性遗忘，也就是模型记住了新的知识，但是把之前训练过的知识给忘记了；且微调也需要一定的成本，并不是一个可以随意执行的操作。

2.3. Agent化

ChatGPT刚刚推出时，其交互模型是简单的多轮会话聊天，还不具备和外界环境直接交互的能力，但Agent化的基础范式实际已经在2022.10由姚顺雨提出[7]，其典型形式是Thought → Action → Observation，也就是要求模型先思考，再行动，然后观察行动产生的结果，如此反复直到完成目标，已经与现在的Agent Loop非常相近了。

随后在2023.06.13，OpenAI发布function calling，模型获得了原生调用外部工具的能力[8]，Agent化从此进入工程可用的阶段，函数调用成为了大模型和外界环境进行交互的标准形式，比如大模型需要获取额外信息，就可以调用Web Search，需要写文件就调用Edit File，这些函数或者Tool实际上都是一些程序员提前写好的程序，大模型只需要负责声明调用，从而保证了参数相同的情况下获得相同的执行结果。

此后 Agent 完成任务的过程，本质上就是一个以 function calling 为核心的循环：模型先判断当前是否需要调用函数，需要就执行函数并把结果回传给模型，如此反复，直到模型可以直接给出最终答案。

    U(["用户输入"]) --> M["模型推理"]
    M --> D{"需要调用函数？"}
    D -->|是| F["执行函数调用
搜索 / 代码 / 数据库"]
    F -->|结果回传| M
    D -->|否| O(["输出结果"])

3. 我们还能做什么

我相信大部分人接触到的工作绝不可能比千禧年问题还要复杂，通过解决千禧年问题，AI已经证明了其智能上限，之所以我们还没有被大规模取代 (在软件开发行业已经有苗头，纯前端/后端岗位已经基本不存在，秋季招聘名额在体感上也大幅度减少)，也只是大部分工作还不值得如此大费周章地用Agent去解决罢了。

所以我们只能在「预算有限」这个前提条件下去探讨大模型时代下人类在工作流里还能主导哪些环节。

3.1 工作流组织

实际软件开发不单单是写一个函数或者写一个类就完事了，其大致流程会涉及到「需求评估」-> 「技术方案调研」-> 「编写技术文档」-> 「代码实现」-> 「测试」-> 「上线部署」。其中每个环节都可以用agent辅助，但是如果要用单个agent跑完整个流程，目前来说效果不好，主要是因为长程任务需要摄入的上下文量远远大于模型的上下文窗口大小，那执行过程中就需要反复执行有损的记忆压缩，会导致后续逐步发生漂移。

更好的方法是引入一个orchestrator agent，工程师负责提出需求和初始prompt，orchestrator负责拆解任务然后在每个流程节点指派另外一个worker agent负责实现，实现完毕后orchestrator推进到下一个节点直到完成为止。

这当然只是理想状态下的情况，现实里会有很多因素制约这套工作流的正常运行，这套工作流能跑起来依赖以下假设：

  • 每一步的验收标准绝对明确
  • 所有业务知识对于agent来说是可达的，也就是agent能够通过内部文档搜索、网络搜索等方式获取到完成任务所需的知识
  • 流程上需要用到的所有平台都提供了CLI或者API，让agent能够与平台进行交互

首先软件开发里的「需求」本身就是不明确的，存在很多模糊甚至矛盾的地方，业务人员或者产品人员在提出需求的时候不可能考虑到全部的情况，就会导致在实际开发过程中会发现新的问题，比如引入这个新功能可能会导致接口性能劣化，这个时候怎么取舍？还是需要工程师跟业务和产品讨论做决策，AI很难知道用户想要什么体验。

其次有很多业务知识agent是获取不到的，比如这一块为什么有一段特判的逻辑，可能是给大客户留的，也可能是为了快速落地留的写死代码，这些决策点不会全部都持久化在内部文档里面，可能只保存在工程师的脑子里面，agent获取不到这部分内容的话自然容易出现漂移。

最后，软件开发过程中需要使用到很多内部基建平台，比如代码管理平台、OLAP平台、部署平台等等，这些平台未必都开发了CLI或者API提供给agent使用，自然就无法代劳。

综上，在工作流组织这方面，比起使用一个orchestrator agent，由工程师来负责会更优，工程师能够明确和沟通需求、知道软件的迭代历史和未被记录的业务知识、自然也能操作大部分平台，且成本更低。但以上问题并非不可解决的，平台CLI是可以开发的，隐性的业务知识会随着agent化进程逐步减少，过往只是因为人力问题所以存在一些未被记录的决策，而agent参与得越多，这些盲区会越来越少。目前仅仅在需求这一块，由于和人类体验有关，暂时没办法全面自动化。

3.2 外挂Memory存储

大模型的参数内化的是过去世界的快照，上下文内容是当前任务的快照；前者意味着大模型没办法随时内化最新的知识，也没办法知道训练时没有接触过的知识，后者意味着大模型没有意识连续性，只要新开一个会话，大模型就无法知道自己之前做过什么事情。

一般解决方法是由外部持久化存储负责管理额外知识和长期记忆，工程师在大模型运行环境 (harness)的某些节点去调用负责记忆或者召回记忆的程序，所以记忆机制是程序化、固定化的，不像大模型的next token prediction那样是语义化的。这些记忆机制也仅仅是解决了「能够存储」的问题，距离「能够被有效利用」还有相当的距离，目前主要是还存在这些问题：

  • 知识和记忆会腐化和过期，程序难以描述这种过程。前一个决策点可能被记录下来了，但是可能第二天做了版本迭代，这个决策点过时了，如果没有及时更新，就会污染记忆；如果人工更新，那工程师每天的工作就只剩维护记忆库了
  • 记忆的触发和召回的触发做不到非常准确。常见的记忆触发时机包括「大模型自主调用」、「会话结束时由程序强制调用」、「消息积累一定程度后由程序调用」，召回时机则包括「大模型自主调用」、「每轮会话强制注入」。这些都和人类的记忆机制相去甚远，人类工作时会自动隐式地在大脑里留下记忆，在遇到相关事件时也可以高效、准确地召回稳定的记忆

无论是openclaw、codex还是claude code的记忆机制我都有尝试使用过，甚至在我自己的项目里我也开发过长期记忆系统，但是对于长期记忆机制，我并没有感觉出对agent工作的正确率有什么巨大的提升 (对于聊天来说memory还是有点用的)。我们可以开发非常tricky的程序，但是这种纯外化的记忆机制跟人脑的记忆终究有巨大的鸿沟，因此在日常和agent合作时，完全可以关掉长期记忆功能，把我们自身当作agent的人肉外挂memory存储。

结合之前提到的「工作流组织」，我们可以把脑内的准确记忆作为优质上下文传给大模型，同时在监督agent工作的过程中把遇到的问题、进行过的决策记忆下来，在横跨新旧会话时，如果agent的行为不符合预期直接纠正即可，目前根本用不上外化的长期记忆机制。

3.3 架构设计

软件架构需要全局判断，包括系统全貌、历史包袱和未来演进，所以主要是两个问题：

  • 架构设计是押注「预期要支持的功能」来做提前设计，但是预期只是判断，不是从代码或者文档里面能够推断出来的
  • 架构的正确性没有明确的检验标准，必须等业务变化之后才能判断架构设计是否优良

由于预期不能用代码或者文档来描述，所以agent很难获取到这部分上下文，只能由工程师把自己大概的想法拿来和agent讨论，不能由agent完全自动化。其次就是架构的检验是模糊的、非标的，没有一个具体的打分标准或者测试程序来验证，agent做了也没办法判断自己做得好不好。

好的架构设计分层明确、职责清晰、可读性和可维护性优良，这不仅对人类工程师有用，对agent展开工作也有很多好处。主要收益来自于明确的分层可以减少模型完成工作的上下文摄入量。比如将软件划分为A层、B层和C层，当某个需求仅涉及到A层的功能变更时，agent只需要阅读A层代码及少量其他层的代码、且只需要修改A层代码就能够完成任务。但如果工程师不对架构进行维护，任由agent把软件变成big ball of mud，大量噪声上下文会降低模型性能也会提高单任务耗费。

从这个角度来看，软件工程里的概念和理论在agent时代还是需要的。

3.4 背锅

无需多言。

4. 总结

大模型的出现代表了智力劳动终于进入到了工业化时代，AI的智能可以随硬件资源的扩大、算法的进步进行scaling和复制，人的智能有上限，而且天才再聪明，智力值和普通人还是处于同一个数量级的。AI运行效率比人脑高得多，只是目前受限于上下文容量、自进化成本高、很多决策点没有标准化等问题，还没办法在日常智力工作中全面取代人类。我们因为高效的记忆机制、拥有意识连续性等原因，还能主导大部分工作，只是在执行细节层面上已经远远比不上大模型。

目前全世界最顶尖的人才都集中到了大模型领域，无论是算法侧还是工程侧，都在飞速发展中，按照目前的趋势来看，智力劳动被AI全面取代的可能性还是不小的，这原本就是开发人工智能的长期愿景，只是转型过程存在阵痛，生产力在飞跃，但是生产关系的变化还存在滞后，给我们这些乱世中的普通人带来不小的心理和生存上的压力。

等到不知道还有多远的将来，人工智能和具身智能能够取代智力劳动和体力劳动时，可以设想到两种可能的社会形态：

  • 人类不再需要劳动，人的价值不再由劳动价值衡量，且无论人是否从事生产，都对生产力高低没有影响。人类迎来真正的大平等时代，人可以出于喜好去劳动，也可以不劳动，社会给人分配生活资料，仅取决于人的内在价值（也就是人仅仅因为存在就有价值，因为存在有益于人类社会的存续）
  • 智能被大公司垄断，同时“必要的”劳动被保留，普通人给AI挖煤、洗数据，这样你才知道自己还在一个存在阶级的社会

不过社会进步是一个多目标优化任务，还存在多方博弈，最后长期会演进到什么地步没有任何人或组织能够预测。短期上，作为普通人的我们只能把握我们还能承担的宏观职能、开拓广度、做1M上下文以外的事情。
